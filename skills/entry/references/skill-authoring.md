# skill 和 plugin 怎么写

> 写或改 skill、plugin 时读。词表在 [SKILL.md](../SKILL.md)。

| 词 | 意思 |
| --- | --- |
| skill | 一个使用者入口：使用者会直接说出、调用或记住的一件事。它的入口文件是 `SKILL.md`。 |
| reference | skill 里的一份细则。agent 到了对应的阶段才读它。 |
| script | skill 里固定、重复执行的机械操作。 |
| 使用者 | 用 skill 的人，通常是 owner。 |

## 按使用者的认知拆 skill，不按内部模块拆

**skill 是使用者入口，不是代码模块。**

- 使用者会直接说出、调用或记住的一件事，才值得做成 skill。
- 使用者不会单独调用的阶段、渠道差异、评分规则，放进 reference。
- 固定、脆弱、重复执行的机械操作，放进 script。不用第二个 skill 假装模块化。
- 不按「调研、撰写、评审」或「平台 A、平台 B」机械地拆 skill。先问：使用者真的把它们当成不同的入口吗？
- 出现了独立的使用者目标、独立的输出和真实的调用，才把 reference 升成 skill。不为想象中的使用者提前拆。

一个复杂的任务可以只有一个 skill。`SKILL.md` 识别意图、做路由。references 放内部的能力。

## 分三层写

1. **Frontmatter**：只写这个 skill 做什么、什么时候触发。把使用者会说的关键词写进 description。
2. **`SKILL.md`**：只放入口必须知道的东西：边界、路由、主流程、必读项、决策门、停止条件、输出。
3. **references 和 scripts**：阶段细节、渠道规则、工具说明、模板、评分、确定性的操作。

不为了显得完整，把所有内容塞进 `SKILL.md`。也不把主流程藏进 reference，让 agent 读完入口还不知道下一步。

## plugin 必须自洽

plugin 运行要用的方法和实现，都在 plugin 里：

- 指令、模板、reference、脚本，放在同一个 plugin 里。
- 不依赖另一个 plugin 里「应该有」的文件。不引用作者机器上的固定目录。不假设使用它的项目已经有一份操作说明。
- 外部服务、MCP、CLI 可以是集成。它们不在时，plugin 必须写明降级或停止的条件，不假装有这个能力。
- 凭证、cookies、登录态不进 plugin。它们留在系统的凭证存储，或项目里 gitignore 的目录。

**运行时的数据不算外部依赖。** 使用者给的文件、项目的人设和配置、历史记录、产出，可以留在项目里。plugin 只定义它们的角色和格式。它们不在时，plugin 写明是询问、创建还是降级。不偷偷猜。

判据：换一台机器、换一个项目，只装这个 plugin。除了凭证和项目数据，完成核心流程还缺不缺别处的一段方法？缺，就是没自洽。

## reference 怎么组织

- 一个 reference 只讲一件事：一个阶段、一个渠道、一个工具，或一份输出契约。
- `SKILL.md` 写清什么情况下读哪一份。不让 agent 猜文件名。
- 一跳直达：`SKILL.md` 直接指向要读的文件，不走 A → B → C 的引用链。
- 共享的规则可以放在单独的目录里。每条路由仍然直接点名要读的文件。
- 一个事实只写在一处。别处链接它，不换个说法再抄一份。
- 会变的渠道规则，写来源、适用范围和验证的日期。一次实验的结果留在项目的记录里，不冒充平台的规律。

**不在开始时读完全部 references。** 渠道越多，这样越慢，也越容易让无关的规则串到一起。

## 每个 skill 写清读什么

每个 skill 在入口写清下面三类。不只列一张文件清单。

**每次开始都读：**

- 当前任务的原始输入，和正在处理的对象。不凭上次的记忆行动。
- 这个 skill 声明为必需的项目上下文。不在，就照约定询问、创建或降级。
- 本轮选中的 workflow reference。一次只选要走的那一条。

**到了对应的阶段才读：**

- 定了渠道、平台或供应商之后，读那一份 channel 或 provider reference。
- 调用工具之前，读这个工具的参数、失败和降级说明。
- 生成或写文件之前，读输出契约或模板。
- 评分、审核、复盘之前，读对应的标准。
- 公开发布、花钱、删除、改线上状态之前，读审批和安全规则，并取得要的确认。

**默认不读：**

- 别的渠道、别的 workflow、背景调研、开源项目的综述、长的示例。
- 只因为「可能有用」才存在的 reference。

入口最好给一张短的路由表：使用者意图 → workflow → 附加的 reference → 必须停下确认的门。

## 简洁

- `SKILL.md` 要短。500 行是上限，不是目标。80 行能讲清，就不写 300 行。
- agent 已经会常识。只写领域约束、真实的踩坑、工具细节，和猜不到的规则。
- 示例只用来说明容易做错的地方。不给每条规则配一个例子。
- 背景和取舍的历史不进运行路径。要保留，就放进 spec 或 reference，只在相关的任务里读。
- 删掉过时的内容，不在旁边加「新版」。入口里同时有两套说法，比没有说明更坏。

## 写完，照这张清单查

1. 使用者要记住几个入口？能不能合成一个自然的任务？
2. 每个 reference 都有明确的读取条件吗？
3. 必读、按需读、默认不读，写清了吗？
4. `SKILL.md` 复制了 reference 的正文吗？
5. plugin 的核心流程依赖外部文件、另一个 plugin，或作者机器上的路径吗？
6. 项目的知识写进 plugin 了吗？运行的数据被打包进 plugin 了吗？
7. 外部写入和撤不回的动作之前，有明确的审批门吗？
8. 文字守 [SKILL.md](../SKILL.md) 的 ASD-STE100 一节吗？有没有写进具体项目的名字？
9. 改了一条规则：同一页的例子，和别的页里说同一件事的地方，在同一次提交里跟着改了吗？
